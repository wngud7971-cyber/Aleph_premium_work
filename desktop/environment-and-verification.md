# 개발 환경과 첫 시제품 검증

확인일: 2026-10-15. 이 문서는 실제 실행한 첫 시제품의 범위와 초기 측정을 기록합니다. 중간 점검 1차 전체 기능 완료 보고서는 아닙니다.

## 확인한 환경

| 항목 | 값 |
|---|---|
| 운영체제 | Windows 11 Home, 10.0.26200, x64 |
| 노트북 모델 | 950XDC/951XDC/950XDX |
| CPU | Intel Core i5-1135G7, 4코어·8논리 프로세서 |
| 물리 메모리 | 약 15.7GiB |
| SDK | .NET 10.0.402, 프로젝트의 `.tools/dotnet`에 설치 |
| 실행 런타임 | Microsoft.NETCore.App / Microsoft.WindowsDesktop.App 10.0.13 |
| 저장 라이브러리 | Microsoft.Data.Sqlite 10.0.13 |
| 배포 형식 | Windows x64, 런타임 포함 폴더, WPF 단일 앱 프로세스 |

처음에는 기본 설치 위치와 PATH에 .NET이 없었습니다. Microsoft 공식 설치 스크립트로 프로젝트 전용 SDK를 받았고 시스템 PATH를 변경하지 않았습니다. 앱은 Windows 로그인 자동 실행을 등록하지 않았습니다.

개발 도구·패키지를 받는 동안만 인터넷을 사용합니다. 앱의 기록·설정·표시는 인터넷 연결을 요구하지 않습니다.

## 저장 검사

`Pds.Checks`의 독립된 임시 DB 검사 15개를 통과했습니다.

- 빈 날짜, 최초 저장과 버전, 새 연결로 다시 열기.
- 따옴표·SQL처럼 보이는 제목을 매개변수 값으로 안전하게 저장.
- 완료 체크와 날짜별 건수 연결, 수정 시 계획 ID 유지, 삭제 후 건수 제거.
- 빈 제목·거꾸로 된 시간 거부, 검증 실패 시 원본 유지.
- 오래된 편집본의 덮어쓰기 거부, 실제 트랜잭션 중 오류가 나도 이전 내용·버전 보존.
- 날짜 범위 경계, 더 새로운 DB 형식을 기존 앱이 덮어쓰지 않고 중단.

실제 WPF 실행에서도 계획 입력 → 저장 → 완료 저장 → 제목 수정 → 저장 → 앱 종료 → 새 프로세스로 재실행 후 기록과 소형 모드 복원을 확인했습니다. 개인 기록 폴더가 아닌 별도 검증 폴더를 사용했습니다. 검사 모드는 개인 폴더를 기본 대상으로 사용하지 않습니다.

## 화면 확인

실행한 WPF 화면을 이미지로 저장해 일반·소형 배치를 확인했습니다. 날짜 칸의 가로·세로 차이가 1 DIP 이내인지 실행 중 검사했습니다. 이 검사는 키보드·스크린 리더·여러 화면 배율의 전체 접근성 검증을 대신하지 않습니다.

## 성능 측정 방법과 한계

- Release, 디버거 없음, 런타임이 포함된 실행 파일을 사용했습니다.
- 계획 1건을 추가·수정·완료 처리한 뒤 측정했습니다. 일반 창에는 날짜 상세가 열려 있습니다.
- 일반 창 준비 후 20초, 소형 모드 전환 후에도 20초를 두었습니다. 각 상태에서 10초 CPU 평균과 구간 마지막의 메모리를 읽었습니다.
- CPU는 프로세스 CPU 시간 증가량을 실제 경과 시간과 논리 프로세서 수 8로 나눠 정규화했습니다. 모든 코어를 합친 전체 용량 대비 비율입니다.
- 입력 커서의 깜빡임을 제외한 캘린더 대기를 확인하기 위해 저장·모드 버튼에 포커스를 두었습니다. 입력창에 커서를 놓은 편집 대기는 별도 조건입니다.
- Working Set과 Private Bytes는 서로 다른 값으로 구분합니다. 표의 MB는 바이트를 1,048,576으로 나눈 값입니다.
- 이미지 저장은 측정 후에 수행해 이미지 인코더 초기화가 수치에 섞이지 않도록 했습니다. 강제 GC나 작업 집합 비우기는 사용하지 않았습니다.

아래 값은 짧은 초기 표본입니다. 계획서의 **5분 평균·최대 CPU, 시작 5회, 30분 상주, 큰 데이터, 저장·조회 반복 지연** 검증은 아직 수행하지 않았습니다. 150MB·1% 등 최종 성능 목표를 충족했다고 단정하지 않습니다. 동시에 실행 중인 다른 앱을 통제한 비교 실험도 아닙니다.

## 마지막 검증의 초기 측정 결과

원본: `artifacts/verification-accepted-20261015-225200/verification.json`. 같은 폴더의 `reopen.json`에서 새 프로세스의 기록·소형 모드 복원 성공을 확인했습니다.

| 상태 | Working Set (MiB) | Private Bytes (MiB) | 10초 평균 CPU |
|---|---|---|---|
| 일반 창 + 날짜 상세 | 139.7 | 72.4 | 0% |
| 소형 모드 | 143.5 | 71 | 0% |
| 트레이 숨김 | 145.4 | 72.8 | 0.234% |

프로세스 시작부터 첫 데이터 준비까지 약 1.56초였습니다. 반복 실행 5회의 통계가 아니므로 시작 성능 목표 달성 판정에는 사용하지 않습니다.

앞선 짧은 실행들에서는 Working Set 약 148~167MiB와 모드 전환 직후 CPU 상승도 관찰했습니다. 준비 시간·입력 포커스·이미지 저장 시점·실행 환경에 따라 초기 값이 달라졌으며, 마지막 값만으로 일정한 메모리 상한을 보장하지 않습니다. 원인은 완전히 분리해 규명하지 않았습니다. 동일 조건의 장기·반복 측정과 경량화를 이어갑니다.

실행 묶음은 루트 파일 합계 약 156MiB입니다. 이는 디스크 용량이며 실행 중 메모리와 다른 지표입니다. 개발 SDK와 패키지 캐시는 별도입니다.

최종 패키지에서 계획 저장·완료·수정·미저장 입력 분리·정사각형 칸과 재실행 복구를 확인했고, 화면 크기 전환 중 복원 크기가 최소값으로 덮이는 문제와 창 재표시 시 중복 초기화 가능성을 수정했습니다. 새 실행 파일로 재검증했습니다.

측정 뒤 캡처 이미지의 투명 배경 합성만 보완했고, 실행 묶음을 다시 빌드해 별도 프로세스의 기록·모드 복구와 두 화면의 정사각형 칸 검사를 한 번 더 통과했습니다. 이 후속 재검증에서는 10초 성능 표본을 새로 수집하지 않았습니다.
